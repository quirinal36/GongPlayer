# 결정 기록

이미 내린 결정과 그 이유를 적습니다. 같은 논의를 반복하지 않기 위한 문서입니다.

결정을 뒤집을 수는 있습니다. 다만 "다시 볼 조건"에 해당하는 일이 실제로 생겼을 때 뒤집고, 뒤집은 내용을 여기에 덧붙입니다. 새 결정은 번호를 이어서 추가합니다.

## 내린 결정

### D1. 언어는 Rust

- **날짜**: 2026-11-13
- **이유**: 재생 속도는 디코더(FFmpeg와 GPU)가 정하고, 언어는 시작 시간, 크기, 메모리, 개발 속도만 좌우합니다. 런타임과 GC가 없는 네이티브 언어면 성능은 같습니다. 그중 Rust는 Concat에서 이미 쓰고 있어 FFmpeg 연동 경험을 그대로 쓸 수 있고, 여러 스레드가 큐로 이어진 구조에서 흔한 데이터 레이스를 컴파일 단계에서 막아 줍니다.
- **버린 대안**: C/C++ (성능과 크기는 같지만 얻는 것 없이 안전성과 빌드 편의를 잃음), C#/.NET (런타임과 GC), Electron/Tauri (웹뷰가 무겁고 HEVC가 다시 OS에 의존)
- **다시 볼 조건**: 없음

### D2. FFmpeg를 직접 연동한다 (libmpv를 쓰지 않는다)

- **날짜**: 2026-11-13
- **이유**: 목표가 "가장 가벼운"입니다. libmpv는 며칠이면 완성되고 재생 품질도 뛰어나지만, DLL이 수십~100MB대이고 쓰지 않는 기능이 대부분입니다. 직접 연동하면 필요한 디코더만 넣어 수 MB로 줄일 수 있습니다.
- **버린 대안**: libmpv, libVLC
- **다시 볼 조건**: M2까지 진행했는데 동기화 품질이 받아들일 수준에 못 미치고 원인을 좁히지 못할 때

### D3. OS의 코덱 프레임워크(Media Foundation)를 쓰지 않는다

- **날짜**: 2026-11-13
- **이유**: PC에 깔린 코덱에 따라 재생 여부가 갈리는 것이 이 프로젝트를 시작한 문제입니다. D3D11VA는 GPU 드라이버와 직접 통신하므로 스토어의 HEVC 확장이 없어도 하드웨어 디코딩이 됩니다.
- **다시 볼 조건**: 없음

### D4. UI 툴킷 없이 Win32와 Direct2D로 그린다

- **날짜**: 2026-11-13
- **이유**: 화면에 그릴 것이 버튼 몇 개와 탐색 바뿐입니다. 툴킷은 수 MB의 크기와 시작 시간, 그리고 영상 텍스처를 툴킷의 렌더러에 넘기는 문제를 함께 가져옵니다.
- **버린 대안**: Slint (Concat에서 쓰지만 이 용도에는 과함), egui, WinUI
- **다시 볼 조건**: 컨트롤이 지금의 두 배 이상으로 늘어날 때. 그 전에 범위가 불어난 것은 아닌지 먼저 봅니다.

### D5. 화면 출력은 Direct3D 11과 VideoProcessor

- **날짜**: 2026-11-13
- **이유**: D3D11VA가 내놓는 텍스처를 같은 디바이스에서 복사 없이 화면까지 보낼 수 있습니다. VideoProcessor가 색 변환, 크기 조절, 회전을 한 번에 처리하므로 셰이더를 직접 쓰지 않아도 됩니다.
- **버린 대안**: wgpu (Windows에서 D3D12나 Vulkan 위에서 돌아 D3D11 디코더 텍스처를 받지 못하므로 시스템 메모리를 거치는 복사가 생김. 의존성도 큼), 직접 셰이더 변환 (코드가 늘고 드라이버별 제약이 있음)
- **다시 볼 조건**: HDR 변환 품질이 드라이버마다 크게 달라 받아들일 수 없을 때. 그때는 색 변환만 직접 셰이더로 옮깁니다.

### D6. 동기화의 기준은 소리 시계

- **날짜**: 2026-11-13
- **이유**: 사람은 소리의 끊김에는 민감하고 영상 프레임 하나의 지연에는 둔감합니다. 소리를 그대로 흘려보내고 영상을 거기에 맞추는 편이 구현도 단순합니다.
- **버린 대안**: 영상 기준 (소리를 늘이고 줄여야 함), 외부 시계 기준
- **다시 볼 조건**: 없음

### D7. 배속은 libavfilter의 `atempo`

- **날짜**: 2026-11-13
- **이유**: 음정을 유지하고, FFmpeg에 이미 들어 있어 의존성이 늘지 않습니다. 2배를 넘는 배속은 2배 이하 단계를 이어 붙여 품질을 지킵니다.
- **버린 대안**: Rubber Band (품질은 더 좋지만 GPL이고 의존성 추가), 음정이 변하는 단순 리샘플링
- **다시 볼 조건**: 자주 쓰는 배속(1.25~2배)에서 음질 불만이 있을 때

### D8. Windows 전용, x86_64 먼저

- **날짜**: 2026-11-13
- **이유**: 풀려는 문제가 Windows의 문제입니다. 크로스 플랫폼 추상화를 걷어 내면 크기와 복잡도가 줄어듭니다.
- **다시 볼 조건**: ARM64 Windows PC에서 쓸 일이 생길 때 (ARM64 빌드 추가. 다른 OS 지원은 범위 밖)

### D9. Concat과 별도 저장소. Concat 코드는 참고만

- **날짜**: 2026-11-13
- **이유**: Concat 안에 두면 AGPL과 Slint, wgpu 의존성이 함께 딸려 옵니다. Concat의 디코딩은 편집기용(임의 위치 프레임 추출, 시스템 메모리 복사)이라 재생기와 구조가 다릅니다.
- **다시 볼 조건**: 없음

### D10. FFmpeg는 LGPL 구성. 개발 중에는 사전 빌드, 배포는 최소 구성 정적 빌드

- **날짜**: 2026-11-13
- **이유**: 디코딩만 하므로 GPL 구성 요소가 필요 없습니다. 개발 중에는 빌드 시간을 아끼고, 크기는 M6에서 한 번에 줄입니다. 정적 링크가 가능한지는 M0에서 미리 확인합니다.
- **다시 볼 조건**: M0 스파이크 B가 실패하거나, 공개 배포에서 LGPL 재링크 조건을 충족하는 방법을 확보하지 못할 때 (exe와 최소 DLL을 같은 MSIX에 포함). 2026-11-13에 Store 배포 요구를 반영해 검증 범위를 넓혔습니다.

### D11. crate는 하나

- **날짜**: 2026-11-13
- **이유**: 규모가 작습니다. 워크스페이스로 나누면 경계를 관리하는 일이 생깁니다. 모듈로 충분합니다.
- **다시 볼 조건**: 빌드 시간이 문제가 될 때

### D12. 소리 출력은 `cpal`로 시작

- **날짜**: 2026-11-13
- **이유**: 작고, Concat에서 써 본 crate입니다. M2를 빨리 끝낼 수 있습니다.
- **버린 대안**: `windows` crate로 WASAPI 직접 구현 (의존성이 하나 줄고 장치 시계를 직접 읽을 수 있지만 코드가 늘어남)
- **다시 볼 조건**: 소리 시계의 정밀도가 모자라 동기 기준(±40ms)을 못 맞출 때, 또는 M6에서 크기를 더 줄여야 할 때

### D13. 상태를 저장하지 않는다

- **날짜**: 2026-11-13
- **이유**: 설정 파일이나 레지스트리를 쓰기 시작하면 설정 화면으로 가는 길이 열립니다. MVP는 매번 같은 상태로 시작합니다.
- **다시 볼 조건**: 음량이나 이어 보기를 기억하지 못해 실제로 불편할 때 ([SPEC](SPEC.md)의 나중 후보)

### D14. 현재 Windows PC에서 직접 개발하고 검증한다

- **날짜**: 2026-11-13
- **이유**: 사용자가 현재 작업 중인 Windows를 개발·실행 환경으로 지정했습니다. 하드웨어 디코딩과 화면·소리 출력을 작업 중에 직접 확인할 수 있습니다. macOS를 주 개발 장비로 가정했던 문서를 갱신합니다.
- **다시 볼 조건**: 개발 장비가 바뀔 때. 순수 로직과 Windows API를 분리하는 원칙은 유지합니다.

### D15. 공개 배포의 기본 경로는 Microsoft Store의 MSIX

- **날짜**: 2026-11-13
- **이유**: 사용자는 타인에게 배포하고 Microsoft Store에 등록하며, 알 수 없는 게시자 경고 없이 원활하게 설치하기를 원합니다. 기존 Rust·Win32 앱을 MSIX로 패키징하는 방향으로 설계하고, 서명과 설치·업데이트의 세부 기준은 [DISTRIBUTION](DISTRIBUTION.md)을 따릅니다.
- **예산 변경**: 기존 "단일 exe 10MB"는 실행 코드 예산으로 유지하되, DLL을 쓰면 그 합계에 포함합니다. MSIX의 압축 크기와 설치 크기는 따로 측정합니다. Store용 아이콘과 고지문 등 필수 파일을 포함합니다.
- **구현 순서**: M0에서 최소 앱의 패키징과 파일 활성화를 검증하고, M6에서 실제 플레이어의 설치·업데이트·제거 및 Store 제출 준비를 완료합니다. 심사와 공개 여부는 구현 완료와 구분해 기록합니다.
- **다시 볼 조건**: Store 외부의 오프라인 설치 마법사가 필수이거나, 검증 결과 MSIX가 필수 기능을 수용하지 못할 때. 별도 설치 파일의 서명과 업데이트를 추가 설계합니다.

### D16. FFmpeg는 sys crate(`ffmpeg-sys-the-third`)만 쓴다

- **날짜**: 2026-11-13
- **이유**: D3D11VA 하드웨어 컨텍스트, `get_format` 콜백, 필터 그래프 명령(`atempo` 배속 변경), 디스플레이 행렬 같은 부분은 안전 래퍼에 없어 어차피 원시 API를 씁니다. 래퍼를 빼면 직접 의존이 하나 줄고, 래퍼와 원시 API를 섞어 쓰는 경계도 없어집니다. 필요한 작은 소유 래퍼(`Packet`, `Frame`, `CodecCtx` 등)는 `media/ffi.rs`에 둡니다.
- **버린 대안**: `ffmpeg-the-third` (BUILD 초안의 선택)
- **다시 볼 조건**: `media/ffi.rs`의 unsafe 코드가 커져 관리가 어려울 때

### D17. `windows-numerics`를 직접 의존에 넣는다

- **날짜**: 2026-11-13
- **이유**: `windows` 0.62에서 Direct2D 좌표 타입(`Vector2`)이 이 crate에만 있습니다. `windows`가 이미 의존하는 crate라 실행 파일 크기와 빌드 시간이 늘지 않습니다. 직접 의존은 4개로 예산(5개) 안입니다.
- **다시 볼 조건**: `windows`가 이 타입을 다시 내보낼 때

### D18. C 런타임은 정적 링크

- **날짜**: 2026-11-13
- **이유**: MSVC 기본(`/MD`)이면 실행 파일이 `vcruntime140.dll`에 의존해, VC++ 재배포 패키지가 없는 깨끗한 Windows에서 실행되지 않습니다. `+crt-static`으로 넣어도 실행 파일 증가는 약 100KB입니다. UCRT(`api-ms-win-crt-*`)는 Windows 10부터 OS에 있습니다. MSIX의 VCLibs 프레임워크 의존성을 선언하는 방법보다 단순합니다.
- **다시 볼 조건**: 정적 FFmpeg(MSVC `/MD`로 빌드)와 CRT 종류가 충돌할 때. 그때는 FFmpeg도 `/MT`로 빌드하거나 VCLibs 의존성으로 바꿉니다.

### D19. 소프트웨어 디코딩 프레임은 swscale 없이 직접 NV12/P010으로 옮긴다

- **날짜**: 2026-11-13
- **이유**: 폴백 경로에서 필요한 변환은 평면 YUV(4:2:0, 4:2:2, 4:4:4, 8~16bit)와 NV12/P010, 회색조를 NV12/P010으로 옮기는 것뿐입니다. 화소 형식 설명(`AVPixFmtDescriptor`)을 읽어 색차를 2x2로 솎는 수십 줄로 충분해 `swscale`이 필요 없습니다. RGB, 팔레트 형식은 지원하지 않고 한 줄 오류로 알립니다. 아래 "아직 정하지 않은 것"의 `swscale` 포함 여부를 닫습니다.
- **다시 볼 조건**: 4:2:2/4:4:4 영상의 색 번짐이 눈에 띌 때 (지금은 최근접 솎기)

### D20. 스왑체인은 버퍼 3장, 최대 프레임 지연 2, 매 프레임 대기 객체를 기다린다

- **날짜**: 2026-11-13
- **이유**: 기준 PC에서 실측했습니다. (1) 대기 객체를 일부 프레임에서만 기다리면 `Present`가 수직 동기까지 막혔고, 그동안 D3D 디바이스 잠금 때문에 디코더도 화면 갱신(60fps)에 묶여 3배속 이상에서 영상이 멈췄습니다. 매 프레임 그리기 전에 기다리게 고친 뒤 패킷당 디코딩이 16ms에서 0.3ms로 줄었습니다. (2) 지연 1, 버퍼 2장에서는 DWM 합성 시점을 놓쳐 갱신을 통째로 건너뛰는 일이 10~20초마다 있어 1080p60에서 프레임이 4~7장씩 누락됐습니다. 지연 2, 버퍼 3장에서는 시작 직후를 빼면 누락이 없었습니다. 늘어난 한 갱신만큼의 지연은 프레임을 고를 때 한 갱신 주기만큼 앞을 보는 것으로 보정합니다.
- **다시 볼 조건**: 입력 반응(탐색 100ms)이나 립싱크 측정에서 한 프레임의 지연이 문제가 될 때

### D21. 시계의 배속은 새 배속의 소리가 스피커에 닿을 때 바꾼다

- **날짜**: 2026-11-13
- **이유**: 배속을 바꾸는 순간 링 버퍼와 장치에는 이전 배속의 소리가 0.1~0.2초 남아 있습니다. 시계를 바로 바꾸면 소리 시계와 170ms 넘게 어긋나 영상이 한 번 튑니다. 소리가 있으면 렌더 스레드가 소리 관측값의 배속을 따라 시계 배속을 바꾸고, 소리가 없거나 장치가 없으면 바로 바꿉니다. 실측 오차가 9~41ms로 줄어 튀지 않습니다.
- **다시 볼 조건**: 없음

### D22. HDR→SDR은 VideoProcessor에 맡기되, 드라이버의 지원 여부 보고는 믿지 않는다

- **날짜**: 2026-11-13
- **이유**: 기준 PC의 NVIDIA 드라이버는 `CheckVideoProcessorFormatConversion`에서 PQ/HLG 입력을 "지원 안 함"으로 보고하지만, 실제로 그 색공간을 지정하면 변환합니다 (합성 HLG 영상은 자연스러운 SDR로, PQ는 100니트 기준으로 잘림). 보고를 믿고 SDR BT.2020으로 해석하면 HDR이 바래 보입니다. 그래서 HDR 색공간을 바로 지정하고, `VideoProcessorBlt`가 실패할 때만 SDR BT.2020으로 낮춥니다.
- **알려진 한계**: PQ는 톤 매핑 없이 잘립니다. 밝은 장면의 하이라이트가 하얗게 날아갈 수 있습니다. 실제 아이폰 HLG 영상과 HDR10 영상으로는 아직 확인하지 못했습니다.
- **다시 볼 조건**: 실제 HDR 영상에서 하이라이트 손실이나 색 차이가 받아들일 수 없을 때. D5에 따라 색 변환만 셰이더(PQ/HLG EOTF, 톤 매핑, BT.2020→709)로 옮깁니다.

### D23. 실측에 맞춰 예산 세 항목을 고친다

- **날짜**: 2026-11-13 (같은 날 사용자 승인)
- **첫 프레임 200ms → 400ms**: 기준 PC에서 `D3D11CreateDevice` 하나가 230~250ms 걸립니다 (NVIDIA 사용자 모드 드라이버 적재, 디바이스 플래그와 무관함을 확인). 그 뒤 파일 열기 10ms, 하드웨어 디코더 첫 프레임 40~50ms를 더해 350~380ms가 나옵니다. D3D11을 쓰는 한 이 PC에서 200ms는 맞출 수 없습니다. 파일 열기를 디바이스 생성과 겹치는 개선은 10ms 정도라 미뤘습니다.
- **메모리 100MB → 재생에 더해지는 양 60MB**: 파일 없이 창만 띄워도 개인 바이트가 72MB입니다 (D3D11, 드라이버, Direct2D, FFmpeg DLL). 앱이 줄일 수 있는 것은 재생에 더해지는 양이라, 측정 대상을 그것으로 바꿨습니다. 패킷 큐를 비트레이트 기준으로 줄여 1080p60에서 +64MB → +53MB가 됐습니다.
- **프레임 누락 0 → 주사율 차이 제외**: 60fps 영상을 59.94Hz 화면에 1배속으로 내면 약 17초마다 한 장은 내보낼 자리가 없습니다. 화면 주사율을 바꾸지 않는 창 모드 플레이어에서는 피할 수 없어, 화면 갱신을 놓쳐서 생긴 누락만 셉니다.
- **설치 패키지 목표 (새로 정함)**: 배포용 MSIX가 압축 2.47MB로 나와 "압축 5MB 이하"를 목표로 정했습니다. dav1d를 넣을지 정할 때 이 여유를 씁니다.
- **다시 볼 조건**: 사용자가 원래 예산을 유지하기로 하면 첫 프레임은 디바이스 생성을 창 표시 전에 미리 시작하거나 다른 GPU에서 다시 재고, 메모리는 FFmpeg 최소 구성 뒤 다시 잽니다.

### D24. 배포용 FFmpeg는 MSVC로 빌드한 최소 구성을 실행 파일에 정적 링크한다 (스파이크 B 결론)

- **날짜**: 2026-11-13
- **결과**: MSYS2 셸에서 `--toolchain=msvc`로 FFmpeg 9.0.2를 최소 구성 정적 라이브러리로 빌드해 `x86_64-pc-windows-msvc` 실행 파일에 링크했습니다 (`scripts/build-ffmpeg-static.ps1`, 약 4분). 실행 파일 하나 6.35MB(예산 10MB), MSIX 압축 2.47MB, 설치 6.44MB입니다. FFmpeg DLL도 VC++ 런타임 DLL도 필요 없습니다. 기준 PC에서 H.264, HEVC 10bit 4K60(하드웨어), HEVC 4:2:2(소프트웨어), VP9, AC-3 5.1, Opus, 회전, 손상 파일을 이 빌드로 재생했습니다. D10의 "배포는 최소 구성 정적 빌드"를 그대로 따르고, D10의 툴체인 미결 항목을 닫습니다.
- **알아낸 것**:
  - FFmpeg 9.0.2에서는 `*_d3d11va2` 하드웨어 가속만 켜면 링크되지 않습니다 (해당 구현 파일이 `*_d3d11va`를 켤 때만 컴파일됨). 두 이름을 모두 켭니다.
  - CRT는 `-MT`로 빌드해 실행 파일의 정적 CRT(D18)와 맞춥니다.
  - 정적 FFmpeg에는 시스템 라이브러리 `bcrypt`가 필요합니다 (`build.rs`가 `static-ffmpeg` 기능에서 추가).
  - `--disable-autodetect`로 zlib, schannel 같은 자동 의존을 막습니다.
- **알려진 차이**: 처음 구성에는 libdav1d가 없어 AV1 하드웨어 디코딩이 없는 GPU에서 AV1을 재생하지 못했습니다. D25에서 넣었습니다.
- **남은 일**: 정적 링크에서 LGPL을 지키려면 사용자가 수정한 FFmpeg로 다시 링크할 수 있는 자료(GongPlayer의 목적 파일 또는 소스와 빌드 방법)를 함께 내야 합니다. 프로젝트 라이선스와 공개 여부에 따라 방법이 달라지므로 그 결정과 함께 정합니다.
- **다시 볼 조건**: 라이선스 검토에서 정적 링크의 재링크 자료를 낼 수 없다고 결론 나면, 같은 최소 구성을 DLL로 빌드해 MSIX에 넣습니다 (`--enable-shared`).

### D25. dav1d를 넣는다

- **날짜**: 2026-11-13 (사용자 결정)
- **이유**: AV1 하드웨어 디코딩이 없는 GPU가 아직 많습니다 (기준 PC의 RTX 2060 포함). 넣지 않으면 그런 PC에서 AV1이 열리지 않아 원칙 1("PC에 따라 재생 여부가 갈리지 않는다")에 어긋납니다.
- **방법**: dav1d 1.5.4를 meson과 MSVC로 정적 빌드(`/MT`, 8bit와 10bit만, nasm 어셈블리 사용)해 FFmpeg `--enable-libdav1d`로 넣습니다. `scripts/build-ffmpeg-static.ps1`이 meson·ninja를 `.deps/pytools` 가상 환경에 설치하고 함께 빌드합니다. Rust 쪽은 `build.rs`가 `dav1d.lib`를 링크합니다.
- **비용**: 실행 파일 6.35MB → 8.13MB (예산 10MB), MSIX 압축 2.47MB → 3.18MB (목표 5MB). 기준 PC에서 4K 10bit AV1을 소프트웨어로 30fps 재생했습니다.
- **라이선스**: BSD 2-Clause. 고지문과 원문(`DAV1D_LICENSE.txt`)을 패키지에 넣습니다.
- **다시 볼 조건**: 크기 예산이 모자랄 때. AV1 하드웨어 디코딩이 흔해지면 다시 봅니다.

### D26. GongPlayer의 라이선스는 MPL-2.0, 소스는 공개

- **날짜**: 2026-11-13 (사용자 결정)
- **이유**: 저장소는 이미 공개되어 있습니다. MPL-2.0은 파일 단위 카피레프트라, 다른 사람이 GongPlayer의 파일을 고쳐 배포하면 그 파일을 공개해야 하지만, 새로 더한 자기 파일은 다른 라이선스로 둘 수 있습니다. MIT보다 "가져가서 고친 뒤 닫는 것"을 막고, GPL보다 Store 배포와 충돌할 여지가 적습니다.
- **FFmpeg(LGPL 2.1+) 정적 링크와의 관계**: 사용자가 FFmpeg를 바꿔 다시 링크할 수 있어야 합니다. GongPlayer 전체 소스와 빌드 스크립트(`scripts/build-ffmpeg-static.ps1`, `scripts/deps.lock`)가 공개되어 있으므로 이 조건을 채웁니다. 배포할 때는 다음을 지킵니다.
  - 배포한 바이너리에 대응하는 FFmpeg와 dav1d 소스 압축 파일을 같은 GitHub Release에 함께 올립니다 (외부 주소만 걸지 않음).
  - Store에는 Microsoft 표준 사용권 계약 대신 자체 사용권 조건을 지정합니다. 표준 계약의 리버스 엔지니어링 금지가 LGPL 2.1 제6조와 맞지 않을 수 있기 때문입니다. 자체 조건은 "이 앱은 MPL-2.0이며 포함된 제3자 구성 요소는 각자의 라이선스를 따른다"는 취지로 `LICENSE`와 `THIRD_PARTY_NOTICES.md`를 가리킵니다.
- **법률 자문 아님**: HEVC 등 코덱 특허는 이 결정과 별개로 공개 배포 전에 확인합니다.
- **다시 볼 조건**: 외부 기여를 받기 시작할 때 (기여 조건을 정함)

### D28. 앱 아이콘은 불꽃 다섯 개가 그려진 공

- **날짜**: 2026-11-13 (사용자 결정)
- **내용**: "공"(Gong)이 ball을 뜻하는 데서 온 디자인입니다. 사용자가 Gemini로 만든 그림에서 공 부분만 외곽선을 따라 잘라 1024px 투명 PNG(`packaging/source/icon-ball.png`)로 두고, `scripts/make-assets.ps1`이 이것으로 실행 파일 아이콘(16~256px)과 MSIX 로고를 만듭니다. 원본 그림의 배경과 생성 표시는 쓰지 않습니다.

- **다시 볼 조건**: 작은 크기(16~24px)에서 알아보기 어렵다는 의견이 있을 때. 작은 크기 전용으로 단순화한 그림을 따로 둡니다.

### D29. GitHub Release로 설치 프로그램과 포터블 ZIP도 제공한다 (서명 없음)

- **날짜**: 2026-11-13 (사용자 요청)
- **내용**: Store(D15)와 함께 GitHub Release를 보조 배포 경로로 둡니다. `scripts/package-release.ps1`이 정적 빌드로 다음을 만듭니다.
  - `GongPlayer-<버전>-setup.exe`: Inno Setup 6. 관리자 권한 없이 `%LOCALAPPDATA%\Programs\GongPlayer`에 설치하고, 시작 메뉴 바로 가기, 제거 항목, 9개 확장자의 "연결 프로그램" 등록(HKCU)만 합니다. 기본 앱은 바꾸지 않습니다.
  - `GongPlayer-<버전>-portable.zip`: 실행 파일 하나와 라이선스 문서.
  - 정적으로 넣은 FFmpeg와 dav1d의 소스 압축 파일, `SHA256SUMS.txt` (D26의 LGPL 의무).
- **서명**: 하지 않습니다. 다운로드한 설치 프로그램은 SmartScreen 경고("Windows의 PC 보호")가 나오며, 사용자가 "추가 정보 → 실행"을 눌러야 합니다. 경고 없는 설치는 Store 경로가 맡습니다. 개발용 자체 서명 MSIX는 다른 PC에 설치되지 않으므로 Release에 올리지 않습니다.
- **왜 MSI가 아니라 Inno Setup인가**: 사용자 단위 설치, 연결 프로그램 등록, 제거를 스크립트 하나로 짧게 쓸 수 있고, 결과가 실행 파일 하나라 받기 쉽습니다. 빌드 장비에만 필요한 도구이며 앱의 의존성은 늘지 않습니다.
- **확인 (기준 PC)**: 조용한 설치 → 설치 폴더, 시작 메뉴, 제거 항목, 연결 프로그램 등록 확인 → 등록된 연결로 `TestVideos/a.mp4`를 열어 경로 전달 확인 → 제거 후 폴더, 바로 가기, 레지스트리가 모두 지워짐.
- **알려진 한계**: 앱 안에 업데이트 확인 기능이 없으므로(원칙 8, D15) Release로 받은 사용자는 새 버전을 직접 받아 덮어 설치해야 합니다. 같은 `AppId`라 덮어 설치하면 업데이트됩니다.
- **다시 볼 조건**: 서명 없는 경고 때문에 사용자가 설치하지 못한다는 의견이 많을 때 (코드 서명 인증서 검토)
